# 手机端设计

> 状态：设计草案，尚未实现。「待定」一节的问题要先定下来再动手。

手机端是 Antumi 的又一个客户端，用来离开电脑时跟进会话：看 Agent 在做什么、回答它的确认和提问、发一句话让它继续、必要时打断它。写代码、看 diff、管理 Git 和设置仍在电脑上做。

第一版只做 Android，不上应用商店，在 GitHub Releases 提供 APK 下载；iOS 的做法见「分发」。

第一版不需要服务器：手机和电脑在同一个局域网，或者都连着用户自己的 Tailscale / ZeroTier 时可用。不装这类工具也想在外面用，或者 App 关着也要收推送，属于后面的阶段，届时才引入一个中转服务（见「阶段三」）。

## 信任模型

先说清楚手机能做到什么程度，后面的限制都从这里来：

- **可操作的手机等于一个可信的远程控制端。** 能发消息，就能让 Agent 在会话**当前的权限模式**内做任何事：权限模式是「自动接受编辑」时，一句话就能让它改文件、提交代码，不会再问。这不是网关能拦住的，拦住它就等于不让手机发消息。
- **手机不能放宽权限。** 它不能把会话改成更宽的权限模式，不能「本会话都允许」或「始终允许」，也不能在执行计划时选「全部放行」。权限只能在电脑上放宽。
- **只读的手机只能看。** 配对时由用户在电脑上选「允许查看」还是「允许查看和操作」。
- 手机丢了的应对办法是在电脑上撤销这台设备，见「设备撤销」。

## 目标与范围

| 阶段一 | 阶段二 | 不做 |
|---|---|---|
| 会话列表（等你、在跑、最近）、读聊天记录 | 发图片、在最近项目里新建会话 | 终端、文件编辑、Git |
| 逐次批准或拒绝、回答问答卡 | 改模型和推理强度 | 内置浏览器 |
| 发文字消息、打断本轮、继续已停的会话 | 只读任务看板和用量 | 设置、账号、服务商、MCP、插件、来源凭据 |
| | mDNS 重新发现、推送地址 | 删除会话、添加任意项目路径、放宽权限 |

Agent、任务和会话仍在电脑上跑，手机断开不影响它们。电脑休眠或关机时手机只能显示离线。

## 总体结构

```
┌──────── 手机 App ────────┐
│  React Native（Expo）     │
└────────────┬─────────────┘
             │ WebSocket + Noise 加密 + 分片
             │ 局域网 / Tailscale；阶段三可经中转
┌────────────▼─────────────┐
│  gateway  独立进程         │
│  监听、握手、加解密、限流     │
└────────────┬─────────────┘
             │ JSON-RPC over WebSocket（127.0.0.1 + token）
             │ 每台手机一个连接，握手时声明设备
┌────────────▼─────────────┐
│  core                    │
│  设备与配对的持久化、授权裁决 │
└──────────────────────────┘
```

分工：**core 持久化设备、裁决每个请求能不能做；gateway 只管网络和加密。**

### 为什么网关是独立进程

- core 只监听 `127.0.0.1` 这条规则不变，对外的端口由网关持有。用户关掉「手机访问」，端口随网关进程一起消失。
- 网关解析的是来自网络的不可信数据，放在单独进程里，它出问题崩溃不会带走 core。
- 阶段三的中转只接到网关上。

要说清楚的是，**这不是权限隔离**：网关和 core 以同一个系统用户运行，能读到 `core.json` 里的完整 token。网关代码一旦被攻破，就等于 core 被攻破。所以网关要尽量小：不执行命令、不读写项目文件，只做转发；依赖越少越好。

网关代码放在 core 包里（`gateway-main.ts`，和 `mcp-main.ts` 同样做法）。用户在设置里打开「手机访问」后，由 core 启动网关子进程：

- 网关通过 stdin 和 core 保持连接，stdin 断了（core 退出或崩溃）就立即退出，不留孤儿进程。
- 网关异常退出时 core 按退避重启（1、5、30 秒，之后每分钟）；端口被占用时不重试，在设置里提示换端口。
- 关闭开关时 core 结束网关，并等它退出后才报告已关闭。

### 授权在 core 里做

网关为每台手机单开一个到 core 的本地连接，在 `system.hello` 里多带一个可选参数，声明这是哪台手机（`client: { kind: 'mobile', deviceId }`）。core 把这个连接标成手机连接，此后：

- 每个请求先按设备的权限（只读 / 可操作）和白名单检查方法与参数，不通过就拒绝，不进入业务代码。
- 通知只发给手机白名单里的那些。
- 设备被撤销时，core 立即关闭这台设备的所有连接。

规则和处理函数放在一起（`rpc-handlers.ts` 旁边），网关的 bug 不会导致越权。连接是按设备分开的，所以 `watchChat` 这类按连接记录的状态和桌面端完全一样。

## 网络与发现

- 网关默认监听用户在设置里选的网卡（默认是当前的 Wi‑Fi / 以太网和 Tailscale 网卡），固定端口（默认 7820，可改）。
- 来源地址过滤只是减少暴露面的辅助手段，身份只认配对密钥：
  - 只接受私有地址：`10/8`、`172.16/12`、`192.168/16`、`100.64/10`、链路本地、IPv6 ULA；IPv4 映射的 IPv6 地址先还原再判断。
  - `100.64/10` 不等于「用户自己的 Tailscale」，经过 SNAT 或子网路由时看到的也可能是网关地址，所以按来源地址限速只防暴力尝试，不当作身份。
  - 不读取任何转发头（`X-Forwarded-For` 之类）。
- 二维码里带电脑当前的私有地址，以及检测到的 Tailscale 地址和 MagicDNS 名。手机保存这些地址，重连时逐个尝试。
- 阶段二加 mDNS（`_antumi._tcp`）：只用来在同一局域网里找到 IP 变了的电脑，TXT 里的设备 ID 只是提示，连上后仍以握手认出的公钥为准。mDNS 在 Tailscale 上不可用，跨 Tailscale 靠保存的地址和 MagicDNS。
- 电脑休眠会断线。手机显示「电脑离线，上次在线 …」，提示可以在电脑上打开防休眠（已有的 `system.setAwakeMode`）。

## 配对与加密

不用 TLS 证书：局域网 IP 拿不到受信任的证书，自签证书在手机上做证书固定又很麻烦。改为在 WebSocket 之上用 Noise 协议做双向认证和加密，用成熟的实现，不自己拼。以后经过中转用的也是同一套握手，中转只看到密文。

- **首次配对**：`Noise_XXpsk3_25519_ChaChaPoly_BLAKE2s`，配对码作为预共享密钥。
- **之后的连接**：`Noise_XX_25519_ChaChaPoly_BLAKE2s`，双方都要求对方的长期公钥和保存的一致。
- prologue 固定为 `antumi-mobile/<协议版本>`，版本不一致握手就失败，防止降级。
- 每次连接都重新握手，传输密钥不跨连接复用；认证失败或 nonce 用尽立即关闭连接。

### 配对的状态

```
未配对 ──扫码握手成功──▶ 待确认 ──电脑上允许──▶ 已授权（只读 / 可操作）
                           │
                           └──拒绝 / 2 分钟超时 / core 重启──▶ 已拒绝
```

1. 电脑在 设置 → 手机 里点「添加设备」，core 生成一次性配对码（32 字节随机数，5 分钟有效），显示二维码：地址列表、端口、电脑长期公钥、配对码、协议版本。
2. 手机生成自己的长期密钥对，用配对码做 `XXpsk3` 握手。握手里收到的电脑公钥必须等于二维码里的，否则中止。
3. 握手成功的那一刻，core 原子地消费配对码：同一个码只有第一个成功的握手有效，之后无论结果如何都不能再用。
4. 进入「待确认」：这个连接上只允许配对状态消息，不能调用任何业务方法。手机上显示一个 6 位确认码，由握手摘要（handshake hash）算出。
5. 电脑上弹出确认框：设备名（仅供显示，不作为身份）、同一个 6 位确认码、「允许查看」「允许查看和操作」「拒绝」。用户核对两边的码一致再选，确认结果绑定的是这次握手和手机公钥。
6. 允许后记入已配对设备，这个连接直接升级为已授权。拒绝、超时或 core 重启都关闭连接，手机要重新扫码。

没有桌面端、core 跑在服务器上时，用本地命令行完成第 1 步和第 5 步（`antumi mobile pair`，在终端里显示二维码和确认码）。

### 密钥和设备存放

- 已配对设备存进 core 数据库的新表 `mobile_devices`：设备 ID（由公钥算出，不接受手机自报）、显示名、公钥、权限、配对时间、最后在线时间。
- 电脑的长期私钥存在 `~/.antumi/mobile/`，权限 0600，和 `core.json` 同等对待。
- 手机的长期私钥和电脑公钥存在 iOS 钥匙串 / Android Keystore 里，标记为仅本机、不随备份迁移到新手机，换手机就重新配对。

### 设备撤销

- 撤销后，core 立即关闭这台设备的所有连接，此后它的握手都失败；撤销和正在进行的握手或请求并发时，以撤销为准。
- 撤销**不会**撤回已经发出的消息，也不会停止正在跑的 Agent：要停就在电脑上停。
- 撤销没法擦除离线手机上的缓存；手机下次连上被拒时自己清掉。设置页的撤销提示要写明这两点。

## 传输

Noise 的一条传输消息最多 65535 字节，而一个附件块是 512 KiB（Base64 后更大），一页聊天记录也可能很大，所以要在 Noise 之上加一层分片：

- 每条 RPC 帧切成不超过 60 KiB 的加密分片，带消息 ID、序号和结束标记；收齐再交给上层。
- 单条消息重组上限 8 MiB，超时 30 秒；超出就丢弃并断开这个连接。
- 每台设备最多 2 个并发连接、16 个未完成请求；全局最多 8 台设备同时在线。附件上传的并发限制（现在按 core 连接计算）因此也按设备生效。
- 网关按 WebSocket 的发送缓冲做背压，手机读得慢时暂停从 core 读取通知，而不是无限堆积。

聊天记录现在一页就是一整个阶段（stage），没有条目数上限。给 `watchChat` / `chatItems` 加一个可选的 `limit` 参数（只加字段），手机每次只取最近的若干条，更早的再往前翻。

## 手机能调用什么

白名单写在 protocol 里（`MOBILE_METHODS` 及参数规则），由 core 执行。新增 RPC 默认不对手机开放。

| 用途 | 方法 / 通知 | 可操作 | 只读 |
|---|---|---|---|
| 握手 | `system.hello`（`features` 只列手机可用的） | ✓ | ✓ |
| 读会话 | `conversations.list` `get` `watchChat` `unwatchChat` `chatItems`（须带 `before`） `messages` `search` | ✓ | ✓ |
| 回答请求 | `conversations.respond`（参数受限，见下） | ✓ | |
| 发消息 | `conversations.send` `cancelQueued` `sendQueued` `retryTurn` | ✓ | |
| 打断和继续 | `conversations.interrupt`（结束本轮）、`continue`（参数受限） | ✓ | |
| 通知 | `conversations.changed` `deleted` `chatItems` `chatDelta` | ✓ | ✓ |
| 阶段二 | `attachments.*`、`conversations.setOption`（参数受限）、`tasks.list`、`tasks.changed` `tasks.deleted`、`usage.changed` 及用量读方法 | 视方法 | 只读的那部分 |

参数规则：

- `respond`：`decision` 只能是 `allow` 或 `deny`，不能是 `allowForSession`；不能带 `mode`；带 `choice` 时，core 查出这个选项的 `grants`，非空（即会持续放行）就拒绝。问答卡的 `answers` 照常。
- `continue`：不能带 `allowBypass`。注意现有实现里对已在运行的会话调 `continue` 会直接返回，所以「强制传 false」并不能撤销电脑上已打开的绕过审批，规则只能是「不许带」。
- `setOption`（阶段二）：只能改 `model` 和 `effort`，不能改 `permissionMode`。
- 「停下」按钮对应 `interrupt`，只结束本轮；`stop`（结束 Agent 进程）和 `stopBackground`（停后台工具）第一版不开放。

测试除了检查白名单里每个方法都真实存在，还要有反向测试：只读设备调每个写方法都被拒绝；`respond` 带 `allowForSession`、`mode`、持续放行的 `choice` 都被拒绝；名单外的方法和通知都到不了手机。

## 断线恢复与冲突

阶段一不做断点续传，**重连就全量刷新**：

- 重连后重新拉会话列表，对正在看的会话重新 `watchChat` 拿权威快照；之前缓存的请求卡片标成「正在刷新」，刷新前不能回答。
- 合并聊天条目用 `(stageId, itemId)`，`replaceStage` 时整段替换；桌面端 `chat-state.ts` 里已有的合并逻辑抽到 protocol 里共用。
- `send` 带上现有的 `ref`，重试时不会重复发。其他写操作在断线中结果不明时不自动重发，刷新后让用户自己看。
- 上传中的图片绑定在连接上，断线后要重新上传。

多个设备（电脑和手机，或两台手机）回答同一个请求时，core 是最终裁决者：第一份有效回答生效，后到的收到 `chat-request-gone`，手机显示「已在其他设备处理」并刷新。要为每种 Agent 验证这个行为，至少覆盖：电脑和手机同时回答、两台手机同时回答、回答后断线重试。

## 版本兼容

手机 App 的更新要过商店审核，旧版本会长时间存在，所以手机和网关之间有单独的 `MOBILE_PROTOCOL_VERSION` 和能力列表，只加可选字段，破坏性改动才升版本。

- 网关作为 core 的客户端照常检查 `PROTOCOL_VERSION`，它和 core 总是同一个版本一起发布。
- 现有的 `connectRpc` 写死了发送并严格比较 `PROTOCOL_VERSION`，手机端不能直接用它；protocol 里要另做一个手机连接器（握手、分片、版本协商），复用的是 schema 和纯函数，不是这个连接器。
- 现有的 `ChatItemList` 会**直接丢弃**不认识的聊天条目。手机端要在丢弃之前把它们换成一个稳定的占位条目（「此内容请在电脑上查看」），否则新版 core 多了一种条目，旧手机上那段对话就无声地少了一块。

## 手机 App

- 用 React Native（Expo）写，复用 `packages/protocol` 的 zod schema、状态规则和聊天合并逻辑。桌面端的界面组件依赖 DOM，不能复用，手机界面另写。参考项目里 orca、superset、t3code 的手机端也都是 React Native。
- Noise、mDNS 和安全存储的库多半需要原生模块，要用 Expo 的 development build 而不是 Expo Go；选库前先做技术验证。
- 页面：电脑列表 → 会话列表（等你、在跑、最近）→ 聊天页（消息、折叠的工具调用、请求卡片、图片）；阶段二加只读任务看板。
- 只缓存最近打开的会话，用于离线翻看，存在 App 沙盒里；取消配对或被撤销时清掉。
- 视觉沿用 `DESIGN.md` 的颜色和字体令牌，在 React Native 里另写一份对应的主题，不硬编码颜色。

### 平台限制

- **iOS**（做 iOS 版时才涉及）：要声明本地网络权限（`NSLocalNetworkUsageDescription` 和 Bonjour 服务名），首次连接弹系统授权；还要处理 ATS 对明文 `ws://` 的限制（内容已在应用层加密）。进入后台后连接能维持多久由系统决定，不作保证；回到前台一律重新同步。
- **Android**：要在 network security config 里允许对局域网地址用明文 WebSocket；较新的系统版本对访问局域网增加了运行时权限，按目标 SDK 的官方说明处理（待真机核实）。
- 真机验证清单：拒绝和恢复本地网络授权、Wi‑Fi 与蜂窝切换、和其他 VPN 同时开着、电脑换 IP、电脑休眠唤醒。

## 代码组织

手机端放在本仓库的 `packages/mobile`，是 pnpm workspace 的正式成员，和其他 `packages/*` 一样。参考项目也都把手机端放在同一个仓库里：t3code、multica、superset 在 `apps/mobile`，同属一个 workspace；orca 在 `mobile/`，但用独立的 workspace 和 lockfile。

- **直接依赖 `@antumi/protocol`。** 它的主入口除了 zod 不依赖任何东西，也不引用 Node 模块（Node 专用的部分在 `/node` 子入口），在 React Native 里能直接用。手机端只引用主入口，不引用 `/node`。
- **协议和手机端一起检查。** 根目录的 `pnpm typecheck && pnpm test` 包含手机端的类型检查和单元测试，改了 RPC 字段、手机端没跟上就会报错。加一个手机要用的接口，在同一个提交里改 protocol、core 和手机端。
- **手机端专用的协议代码也放在 protocol 里**：手机连接器（握手、分片、版本协商）、`MOBILE_METHODS` 白名单和参数规则、聊天条目合并、会话提醒规则。这些是纯 TypeScript，core、网关、桌面端和手机端共用，不写在 `packages/mobile` 里。
- **打包不进日常验证。** 打 APK 很慢，单独一个命令（`pnpm --filter @antumi/mobile build:android`），在发布和改了原生模块时跑。

要处理的问题：

- **React 版本。** 桌面端和手机端的 React 版本可能不一致（React Native 要求和它配套的那个版本）。pnpm 允许各包用各自的版本，但 Metro 在 pnpm 的符号链接结构下要配置好；搭建时先验证 Expo 的 monorepo 支持，确认桌面端的构建不受影响。
- **安装体积。** React Native 和 Expo 会让每个人 `pnpm install` 多装几百 MB。如果后来明显拖慢了桌面端的开发，改成 orca 的做法：`packages/mobile` 有自己的 workspace 和 lockfile，用 `link:` 引用 `packages/protocol`，并在根目录的 `typecheck` 里显式加上手机端的检查，免得协议改动漏查。
- **版本号和发布。** 手机端的版本号和桌面端分开，用单独的 tag（如 `mobile-v0.1.0`）；`docs/RELEASING.md` 加一节 Android 发布流程；`CHANGELOG.md` 里手机端的改动单独分一组，按手机上看到的名字写。
- **规则文档。** `AGENTS.md` 的进程边界加上：手机端是客户端，只经过网关连接，不直接连 core；授权规则只在 core 里执行。

- 用 Expo 的 EAS Build（或本地构建）打出签名的 APK，和桌面端一起按 `docs/RELEASING.md` 的流程发布，版本号单独计。
- 签名密钥只有一把，离线备份，永远不换：换了密钥，已安装的用户只能卸载重装，本地缓存和配对都会丢。
- App 自己检查 GitHub 上的新版本，下载后交给系统安装器；只改 JS 的修复可以用 EAS Update 直接推送，改了原生模块才需要新 APK。
- 安装说明要配图：允许「安装未知来源应用」，以及小米、华为、OPPO 等系统和 Play Protect 的风险提示怎么处理。
- Google 宣布过要求商店外安装的应用也来自经过身份验证的开发者，分地区逐步执行。发布前要确认当时的政策，必要时注册开发者身份（不需要上架）。
- 很多国产手机没有 Google Play 服务，用不了 FCM，所以阶段二的推送优先接 ntfy 这类自带常驻连接的方案，阶段三也不能只靠 FCM。

**iOS：暂不提供 App**

苹果不允许安装任意安装包。不上架时唯一面向普通用户的办法是 TestFlight 公开链接，但它需要苹果开发者账号（每年 99 美元）和测试版审核，每个版本 90 天后过期；目前没有账号，所以第一版不做 iOS App。之后有两条路：

- **网页版**：网关顺带提供一个网页客户端，iPhone 用浏览器打开。局域网 IP 拿不到正式证书，非 HTTPS 页面不能调用摄像头扫码、不能收 Web 推送，所以配对改为手动输入配对码；配合 Tailscale Serve 时有正式 HTTPS，限制就没了。网页版不能暴露完整的 core RPC，走的仍是同一个网关、同一套授权。
- **以后注册开发者账号**：用同一份 React Native 代码打 iOS 包，走 TestFlight。

开发者用户也可以用 Xcode 和免费 Apple ID 从源码自己装，但 7 天后失效，只写在开发文档里，不作为正式渠道。

## 通知

- **阶段一**：只在 App 处于前台时提醒。后台收不到，界面上要说清楚。
- 「该提醒什么」的规则现在在桌面端渲染进程（`attention.ts` 的 `noticesBetween`），例程、额度等提醒另在 `notifications.ts`。阶段二只把会话提醒（等你确认、本轮结束）需要的那部分做成 protocol 里的纯函数，返回提醒种类和目标，文案由各端按自己的语言生成；桌面端同时改为调用它。
- 推送要由一直在线的网关来判断，而不是靠某台手机的连接：网关自己保持一个 core 连接订阅会话变化。`noticesBetween` 会跳过第一次看到的会话，所以网关启动时要先拿一次快照，把已经在等的请求补成提醒，并按「会话 + 请求 ID」去重。
- **阶段二的过渡办法**：在设置里填一个 ntfy、Bark 之类的推送地址，网关只推「某会话在等你确认」这类短句，不带代码或对话内容。这样不用自建服务器也能收到推送。

## 分阶段

**阶段一：同一网络下跟进会话**
- core：`mobile_devices` 表；`system.hello` 的手机声明和按连接授权；`mobile.status` `mobile.setEnabled` `mobile.beginPairing` `mobile.confirmPairing`（允许查看 / 允许操作 / 拒绝） `mobile.devices` `mobile.revoke` 方法和 `mobile.changed` 通知；网关子进程的启停与重启；`watchChat` / `chatItems` 的 `limit`。
- 网关：监听与地址过滤、Noise 握手、配对状态机、分片与限流、每台设备一个 core 连接。
- 桌面端：设置 → 手机（开关、网卡与端口、二维码、确认框、设备列表、撤销）。
- 手机（Android）：配对、会话列表、聊天页、逐次批准和问答、发文字、打断和继续、重连全量刷新、检查更新。
- 仓库：建 `packages/mobile` 并接入根目录的 typecheck 和 test；验证 Metro 与 pnpm、两个 React 版本共存；更新 `AGENTS.md` 的进程边界。
- 发布：APK 进 GitHub Releases，签名密钥备份；`docs/RELEASING.md` 加 Android 一节。
- 文档：安装 APK 的说明；用 Tailscale 在外面连回电脑的说明。

**阶段二：更完整的手机体验**
- 发图片、在最近项目里新建会话、改模型和推理强度、只读任务看板和用量。
- mDNS 重新发现；会话提醒规则移到 protocol；ntfy / Bark 推送地址。

**阶段三（按需）：中转和推送**
- 一个可自建的中转服务：电脑的网关和手机都主动连上去，中转按设备 ID 转发 Noise 密文，不存消息。
- 用 APNs / FCM 推送，由网关判断何时推送，交给中转的只有提醒种类和会话 ID；手机收到后再连上来取详情。
- 中转能看到的元数据（哪台电脑和哪台手机在通信、什么时候、流量多大），以及 APNs / FCM 凭据和设备 token 由谁保管，要在这一阶段写清楚。
- 中转挂了只影响「在外面且没有 Tailscale」的情况，局域网直连照常可用。

## 安全清单

- core 仍只监听 `127.0.0.1`；对外端口只有网关，只接受私有地址，但身份只认配对密钥。
- 网关是可信代码，被攻破等于 core 被攻破；它保持最小，不执行命令、不碰文件。
- 未配对的连接拿不到任何数据；配对码一次性、5 分钟过期；待确认期间只能收发配对状态；电脑上核对 6 位确认码后才授权。
- 内容端到端加密，每次连接重新握手，prologue 绑定协议版本。
- 授权在 core 里按设备执行：方法、参数、通知三重白名单，新 RPC 默认不开放，手机不能放宽权限。
- 可操作的手机能在当前权限模式内驱动 Agent，这是设计如此，不是漏洞；用户要知道这一点（配对确认框里写明）。
- 撤销立即断开该设备所有连接，但不撤回已发的消息、不擦除离线缓存。
- 分片重组、并发连接、未完成请求都有上限，按设备计算。
