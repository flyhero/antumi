# 来源评论同步

收件箱里的 issue 在导入任务或建立排查会话后成为关注事项。core 启动及每 15 分钟检查一次，独立于收件箱筛选结果；不再分配给当前用户、已被导入隐藏、外部已关闭，都不会使关联丢失。普通收件箱条目仍只同步列表。

## 查看与继续

会话与任务页的「来源更新」显示新增评论、作者、时间和原文链接。「新评论」表示尚未查看，「尚未交给 Agent」表示尚未提交或排队；两者分别持久化。所有未查看评论都已展示后才清除相应查看提示，避免把尚未加载的历史标成已读。

「带新评论继续排查」和「发送到任务会话」只处理点击时范围内、尚未提交的评论。当前回合运行时排到下一回合；原有队列支持取消、暂停和继续。取消后评论可以重新发送。新到达的评论留到下一批，不加入已经确认的批次。每批最多 100 条、约 8 MiB；超出部分保留为尚未发送，可以继续提交，不截断整批内容。

同步不启动 Agent，也不批准计划或切换权限。手动发送恢复原会话并沿用当前权限。待验收、已完成、已取消任务需要先用原有入口继续任务；没有会话的任务只更新原文，下次正常启动时读取。支持结构化评论的任务会在首次提示中附上完整来源参考文件，并记录其中实际包含的评论；未包含的评论继续保留为待发送。团队任务沿用原有团队守卫。

归档会话和完成、取消的任务暂停后台关注，恢复后补拉。关注开关可独立关闭；来源断开、禁用或插件卸载后暂停，缓存保持可读。更换来源站点或账号不会把旧 issue key 自动绑定到新来源，需要恢复原连接。

后台只同步文字，保留之前的图片；「重新拉取」仍抓取完整原文和图片。新增评论里的图片保留原链接，不自动下载。

## 实现边界

`SourceUpdates` 负责关注生命周期、调度、批次和对账；`SourceUpdateStore` 在任务数据库里持久化事项、评论、目标和批次。桌面通过 `source-comments-v1` 能力协商，按目标分页读取，不承载同步或任务状态规则。

同一来源绑定与 issue key 共用抓取缓存，目标各自保存初始基线、已查看位置和投递批次。新目标的基线不能推进已有目标的检查点。初次导入和升级初始化不会把既有评论报成新增。

来源插件声明 `commentSync: 1`，`fetch` 返回对应快照的 `commentState`，`comments` 返回增量页面。SDK 提供 `commentState` 和 `commentPage`：身份采用平台稳定评论 ID；检查点包含最新创建时间与同时间的全部 ID；分页冻结上边界，期间的新评论留待下轮。每页最多 100 条，不能截断为最近 20 条。原文快照仍显示最近 20 条。

core 每轮处理最多 10 页后短暂让出；完整检查点只在分页结束后推进。失败后按 ID 去重重试，过期分页令牌可从完整检查点重新抓取。暂时失败按 15、30、60 分钟退避。认证、权限或事项不存在错误等待重新连接或手动重试。插件不支持评论能力时保留原有手动刷新。

GitHub 支持 Issue 和 PR 的普通讨论评论，不包含 PR 行内审查评论；Jira 使用 ADF 转 Markdown；Linear 使用 GraphQL 评论连接；禅道使用 action ID 或对象映射键，缺少稳定身份时只更新原文，不猜测评论身份。第一版保证新增评论补拉，不提供历史评论编辑、删除的完整审计。

每个发送批次有固定请求 ID 和消息 ref，双窗口请求按目标串行处理。聊天日志中的 `receipt` 表示 daemon 已接收写入；队列与日志用于恢复提交状态。SQLite 和聊天日志无法组成一个事务，若只有出站日志、没有接收凭据，则显示「提交结果待确认」，不盲目重发。core 重启不发送尚未接收的批次。

外部评论始终作为 `<untrusted-source>` 参考资料。较长的批次保存在该会话专属的粘贴文本目录，沿用现有文件读取授权，不把外部评论升级成用户指令。
